# Thehro: Code, Pipeline and How Every Number Was Made

Prototype for the Amazon AI Cyber Security Hackathon, Track 2 (AI-Driven Scam Pattern Recognition).
All data is synthetic, generated by our own simulator. No real customer, bank or platform data was used.

## 2. How to run it

Tested with Python 3.13.

```bash
cd thehro
pip install -r requirements.txt
python scripts/run_all.py            # simulate -> features -> train -> thresholds -> evaluate -> outputs/
python scripts/run_all.py --quick    # same, but skips the 7 held-out scam-type refits (much faster)
python scripts/deck_numbers.py       # prints every derived number used on the slides
python -m pytest -q                  # 20 tests
uvicorn thehro.api:app --port 8000   # start the API, then POST outputs/sample_requests.json to /v1/score
```

`run_all.py` takes about 4-10 minutes on 2 CPUs and about 3 GB of RAM. The held-out refits take the most time.
It is fully seeded (`--seed 7`), so it reproduces the same world and the same numbers.

## 3. Pipeline A: how the results were produced (offline)

```
 1  simulate()                    simulate.py    40,000 customers, 60 days, 2.78M payments, 157 campaigns, 1,675 scam journeys
         │
 2  build_features()              features.py    39 features per payment, using only data from before that payment
         │   └─ detect_campaigns()  campaign.py  mule-network flag from money flows, no labels needed
         │
 3  training_labels()             models.py      days 14-34; label = 1 only if the scam was REPORTED before day 38
 4  fit()                         models.py      journey model, payee model, context model, fused model, scam-type recogniser
 5  score()                       models.py      risk scores for every payment
         │
 6  thresholds_from_validation()  evaluate.py    days 35-41, genuine payments only -> each tier line set to its budget
         │   └─ calibrate()         policy.py
         │
 7  run_policy()                  evaluate.py    test days 42-59: two-family gate, tiers, 7-day memory (starts empty on day 42)
         │   └─ evidence(), base_tiers(), apply_memory()   policy.py
 8  summarise()                   evaluate.py    compare every decision with the hidden truth -> headline metrics
         │
 9  naive_rules()  budget_curve()  stress_tests()  held_out_workflows()  fairness()  campaign_timing()  latency test
         │
10  outputs/metrics.json, tables/*.csv, figures/*.png, model_bundle.pkl, demo_scenarios.json
         │
11  deck_numbers.py                               confidence intervals, "1 in N", per-10-million scenario -> slides
```

What each step does:

1. **Simulate.** Builds the fake world described in section 5. Every payment carries hidden truth: genuine or scam, which
   scam type, which campaign, which victim, and whether and when the victim complained.
2. **Features.** For each payment, 39 numbers are computed from what the bank could know at that moment:
   - **Journey (19):** amount (log), channel, hour, night, new payee, earlier payments to this payee, days since the first
     one, amount vs the customer's usual, vs the previous payment to this payee, growth, new payees in 7 days, payments
     and sum to recent payees in 7 days, money pushed out in 24 h vs usual, payments in the last hour, FD broken in
     48 h, small credits from strangers in 24 h, investor flag.
   - **Payee (12):** payee type, valid account, account age, idle days, new payers in 24 h and 7 days, inflow in 24 h,
     share of inflow passed on in 24 h, registry flag, DoT FRI band, in a live mule network, network size.
   - **Context (8, opt-in only):** on a call, caller not saved, internet call, call minutes, caller FRI band, screen
     sharing, remote-access app, app switches. Without consent these are blank and that family does not vote.
3. **Labels like a real bank.** Only scams reported before day 38 count as scams in training. Unreported scams count as
   genuine. This gave 677 scam labels on 301,467 training payments (loan-fee scam: only 2 labels).
4. **Models.** scikit-learn `HistGradientBoostingClassifier` (300 rounds max, learning rate 0.08, 31 leaves, at least 50
   payments per leaf, L2 1.0, early stopping). Red-flag features are monotonic: a registry flag, screen sharing, an FD
   break and similar signals can only raise risk. One model per family, one fused model on all 39 features, and a
   multiclass recogniser that guesses the scam type for officers (below 0.6 confidence it says "unfamiliar pattern").
5. **Score** every payment.
6. **Set the lines.** On the validation week's genuine payments, each line is placed so genuine payments cross it at the
   budget rate, counted against ALL customer payments (shop payments included): note 1 in 1,000, pause 1 in 10,000,
   hold 1 in 100,000. A family counts as "elevated" above the 99th percentile of genuine scores. Lines found:
   note 0.0107, pause 0.0847; family lines journey 0.0134, payee 0.0101, context 0.0274. The lines are then frozen.
7. **Policy on the test days.** Each payment gets a tier:
   - T1 note: fused risk above the note line.
   - T2 pause: fused risk above the pause line.
   - T3 trusted check: T2 + two families elevated + ₹50,000 or more.
   - T4 hold: two families + outside flag on the payee + hold line + ₹10,000 or more.
   - Memory: after a customer continues past a warning, for 7 days a note becomes a pause and the ₹ lines are waived.
8. **Score against the truth** (including unreported scams): victims warned, false pauses, holds, money protected,
   precision at India's fraud rate.
9. **Extra tests** on the same frozen test days: 3 simple-rule baselines, 7 budget levels, 4 scammer-adaptation stress
   tests, 7 refits each hiding one scam type, fairness by age, language, region and consent, campaign detection speed, and
   1,000 timed decisions through the real decision service.
10. **Save** everything to `outputs/`.
11. **Derive** the slide-ready numbers with `deck_numbers.py` (section 7 has the formulas).

## 4. Pipeline B: the live system (architecture slides 11-13)

```
 Customer taps Pay in the bank app
        │   (before the PIN screen)
        ▼
 Bank backend ── POST /v1/score ──►  DECISION SERVICE (stateless, at the bank)
                                        1 Validate      authentication, data format, consent
                                        2 Features      journey (bank records)
                                                        payee risk (NPCI / MuleHunter.AI, I4C, DoT FRI + our network flag)
                                                        context (opt-in yes/no flags from the bank app SDK)
                                        3 Score         3 family models + 1 fused model        ~25 ms median, 40 ms p99
                                        4 Decide        two-family gate, budget lines, ₹ lines, 7-day memory -> tier 0-4
                                        5 Explain       up to 3 checkable facts + matching advice, English or Hindi
                                               │
             ┌─────────────────────┬───────────┴──────────┬──────────────────────────────┐
             ▼                     ▼                      ▼                              ▼
   Customer screen        Trusted person (T3)     Fraud officer (T4)            Evidence log
   note / pause /         approves by push,       calls within 30 min,          SHA-256 hash chain,
   trusted check / hold   else 1-hour wait,       release or cancel;            pseudonymous, every read logged,
                          then customer decides   no answer = cancelled         1930 / NCRP complaint draft

 POST /v1/outcome         customer choice or officer decision -> appended to the evidence log
 GET  /v1/evidence/{seq}  officer reads one record (role-based access, read logged)
 Learning loop            outcomes + complaints (days late) -> weekly retraining -> lines re-set to budgets -> versioned release
```

Fail-safe rules: a missing field or failed feed counts as "no flag", the decision never waits for a slow feed, and if
the service is down the bank's current rules apply and nothing is held.

In the prototype, the simulator stands in for all three inputs, including the outside feeds. The evidence log is
in memory with the same hash chain. mTLS, device attestation and access roles are proposed, not built.

## 5. How the synthetic data is generated

Everything below is in `thehro/simulate.py` (seed 7). Parameters are illustrative, loosely calibrated to public Indian
figures (sources in `thehro/README.md`).

### 5.1 People and accounts

| What | How it is generated |
|---|---|
| 40,000 customers | Age: 18-25 18%, 26-40 42%, 41-59 27%, 60+ 13%. Segment by age: student, salaried, trader, homemaker, retiree |
| Language | Hindi 44%, English 14%, Tamil 8%, Telugu 8%, Bengali 8%, Marathi 9%, Kannada 5%, Gujarati 4% |
| Region | Metro 35%, tier-2 40%, rural 25% |
| Spending level | By segment x a random lognormal factor; scales every payment amount |
| Investors | 25% of salaried and traders aged 26-59, 15% of 60+, 5% of 18-25, 8% of others |
| Fixed deposits | 5% / 25% / 45% / 70% by age band |
| Opt-in to phone signals | 70% of customers |
| Trusted contact named | 35% of customers aged 60+, 5% of others |
| Other accounts | 12,000 merchants, 3,000 vendors, 150,000 outside individuals, 40 brokers, 4,000 suppliers, 12 crypto exchanges |
| Mule accounts | Created per campaign; new accounts or old accounts that wake up after months of no use |

Age, language and region are stored for the fairness check only. They are never model inputs.

### 5.2 Genuine payments

Each customer makes everyday payments through the 60 days at realistic hours (busiest 6-8 pm): shops (UPI to merchant),
known people, regular vendors, rent, SIP and lump-sum investments, suppliers and cash withdrawals.

To make the problem hard, many genuine payments **look risky**: first payments to new individuals or a new landlord,
medical emergencies and grey-market investments. Each kind has its own chance of happening during a call:

| Genuine kind | On a call | Caller not saved | Median call |
|---|---|---|---|
| Shop payment | 2% | 30% | 3 min |
| Known person | 12% | 10% | 4 min |
| New individual payee | 35% | 70% | 6 min |
| New landlord | 30% | 60% | 8 min |
| Medical emergency | 60% | 70% | 15 min |
| Grey-market investment | 20% | 40% | 12 min |

### 5.3 Scam campaigns

| Scam type | Campaigns | Avg victims each | Runs for | Targets most | Victims who report | Typical report delay |
|---|---|---|---|---|---|---|
| Fake trading / investment | 26 | 20 | 20-40 days | 41-59 and 60+ | 50% | 3 days |
| Digital arrest | 30 | 8 | 10-20 days | 60+ (weight 2.5) | 60% | 1 day |
| Task / part-time job | 22 | 15 | 7-15 days | 18-25 | 40% | 1.5 days |
| Fake customer care | 20 | 10 | 7-14 days | 60+ | 55% | 7 hours |
| Marketplace "scan to receive" | 20 | 10 | 10-20 days | 18-40 | 35% | 12 hours |
| Cloned voice of a relative | 25 | 6 | 5-10 days | 41-59 and 60+ | 55% | 5 hours |
| Fake loan fee (new) | 15 | 14 | 7-15 days, from day 30 | 18-40 | 45% | 2 days |

Campaigns start from day 3 (loan fee from day 30, so it is "new" for the model). Report delays are random (lognormal)
around the typical value. Overall about half of victims ever report.

### 5.4 What each scam journey looks like

| Scam type | Payments | Pattern |
|---|---|---|
| Fake trading | 3-10, about 1.5 days apart | First ₹2,000-60,000, each next about 1.8x the last; 55% get a small fake "profit" credit early; 60% end with a fake "tax" of 15-30% of the total; FD broken 45% of the time for ₹50,000+ |
| Digital arrest | 1-5, 1-20 minutes apart | ₹15,000 to ₹50 lakh each (around ₹70,000 x spending level); FD broken 60% of the time for ₹50,000+ |
| Task / job | 2-7, about 8 hours apart | First 2-3 small "reward" credits of ₹100-800; then ₹1,000-3,000, each about 2.2x the last |
| Fake customer care | 1-4, 2-15 minutes apart | ₹2,000 to ₹2 lakh each (around ₹25,000 x spending level) |
| Marketplace | 1-5, 2-10 minutes apart | Starts ₹500-50,000 (around ₹4,000) and roughly doubles |
| Cloned voice | 1-3, 5-30 minutes apart | ₹5,000 to ₹2 lakh; half get 1-2 tiny "test" credits minutes before |
| Fake loan fee | 2-6, hours apart | "Fees" starting ₹999-4,999, each about 1.6x the last |

Many steps go to a fresh mule account, so the payee is often new to the victim.

### 5.5 Phone context during scams (only seen for customers who opted in)

| Scam type | On a call | Internet call | Median call | Screen sharing | Remote-access app |
|---|---|---|---|---|---|
| Fake trading | 15% | 60% | 12 min | 3% | 2% |
| Digital arrest | 92% | 85% | 150 min | 12% | 4% |
| Task / job | 8% | 50% | 6 min | 1% | 1% |
| Fake customer care | 90% | 20% | 15 min | 60% | 35% |
| Marketplace | 45% | 40% | 6 min | 1% | 1% |
| Cloned voice | 95% | 30% | 8 min | 1% | 1% |
| Fake loan fee | 50% | 50% | 10 min | 5% | 3% |

The caller is almost always unknown to the victim (97-100%).

### 5.6 Money movement and outside flags

- Victims pay first-layer mule accounts. Mules quickly forward most of the money to other mules or cash it out. Small credits
  and "penny drop" test payments also appear in the money trail.
- The mule-network detector (`campaign.py`) only sees these money flows. Slide 7 shows how well it finds them.
- After a victim reports, the accounts involved appear in the simulated outside feeds (I4C registry, network risk, DoT
  FRI) 1-3 days later, as in real life. That is why outside flags alone catch scams late.

### 5.7 What the simulator produced

| Item | Count |
|---|---|
| Payments | 2.78 million over 60 days |
| Scam journeys (victims) | 1,675 in 157 campaigns |
| Scam journeys starting in the test days (42-59) | 720 |
| Scam payments in the test days | 2,680 |
| Customer payments in the test days (incl. shop payments) | 786,121 |
| Scam share of all payments | 0.214%, which is 158-315x reality, so there are enough scams to measure |

## 7. Formulas

**Wilson 95% interval** (victim shares; k victims out of n):

```
p = k / n,  z = 1.96
centre = (p + z²/(2n)) / (1 + z²/n)
half   = z * sqrt( p(1-p)/n + z²/(4n²) ) / (1 + z²/n)
interval = centre ± half
```

**Exact Poisson (Garwood) 95% interval** (rare counts such as false pauses; k events):

```
lower = chi2.ppf(0.025, 2k) / 2        (0 when k = 0)
upper = chi2.ppf(0.975, 2k + 2) / 2
rate interval = [lower, upper] / payments x 10,000
k = 0 gives upper = 3.689 -> 786,121 / 3.689 = 1 in 213,000
```

**Precision at a real fraud rate p** (share of pauses that are real scams):

```
tpr = scam payments paused / all scam payments          = 0.860
fpr = genuine payments paused / all customer payments   = 70 / 786,121
precision = tpr*p / ( tpr*p + fpr*(1 - p) )
p = 13.6 per million -> 0.116 = 1 in 9;   p = 6.8 per million -> 0.062 = 1 in 16
```

**Money protected (modelled)**, per victim, payments in time order:

```
survive = 1, expected_loss = 0
for each payment (amount a, tier k):
    if k >= 2: survive = survive * (1 - STOP_PROB[k][scam type])
    expected_loss += a * survive
protected = total - expected_loss
money protected share = sum(protected) / sum(total)
```

**Thresholds:** `calibrate()` places each line so genuine validation payments cross it at the budget rate, counted
against all customer payments (shop payments included).

**Per 10 million payments a day:** genuine paused = 0.89 / 10,000 x 10,000,000 = 890; scams = 13.6 x 10 = 136;
scam paused = 136 x 0.86 = 117; holds = 136 x 0.48 = 65.

Run `python scripts/deck_numbers.py` to print all of these from `outputs/metrics.json`.

## 8. Notes and known differences

1. **Slide 6 baseline label is shortened.** The row "Pause during calls from unknown numbers" is, in the code, "first
   ₹10,000+ payment to a new payee, only while on a call with an unknown number" (`naive_rules()`). The fraud-list rule
   means the payee is on the registry or in DoT FRI band medium or high.
2. **False-pause upper bound** is 1.125 per 10,000. The deck shows 1.12; `deck_numbers.py` rounds it to 1.13. Either
   way the interval crosses 1 per 10,000, as slide 6 says.
3. **Hold line.** One validation week is too small to set a 1-in-100,000 line, so in this run the hold line equals the
   pause line (0.0847). The extra hold conditions (two families, an outside payee flag, ₹10,000+ and an officer) keep
   genuine holds at 0. Slide 13 says this.
4. **Money protected is modelled**, not measured. It depends on assumed stop rates, to be measured in a pilot.
5. **All results are synthetic.** The simulator is cleaner than reality, so real results will be lower. Only a
   shadow-mode pilot on real data (slide 9, phase 1) can confirm them.
6. The demo page (`demo/template.html`, `outputs/thehro_demo.html`) is in the package but was not part of the submission.
